# Weighted grade calculator for university students

A full-stack TypeScript monorepo implementing a university grade tracker with JWT authentication, PostgreSQL storage, and a React SPA. The system lets students organize subjects by period, define composite subjects (catedra/lab/terreno splits with configurable weights), and enter grades that roll up into weighted averages. The architecture is Express + Prisma on the backend with a Vite + Tailwind frontend deploying to Vercel. Watch for: the backend JWT secret falls through to a hardcoded default in production (confirmed); the frontend sends grade weights as whole integers (0-100) while the backend validates them as decimals (0-1), which will cause every grade creation from the UI to be rejected with a 400 (confirmed); the Vercel deployment config only serves the frontend SPA with no serverless function or external API target, so the backend has no deployment path (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The data model cleanly separates periods, subjects, components, and grades with cascading deletes, and the composite-subject abstraction (multiple weighted components per subject) is well-designed for the stated requirements. The grade calculator service correctly normalizes partial data by dividing weighted sums only by the weights of grades that have values, avoiding distortion when a student hasn't entered all grades yet.

Authentication uses bcrypt + JWT with a 7-day token lifetime stored in localStorage. The auth middleware falls through to `'default-secret'` when `JWT_SECRET` is unset, which in any production deployment means tokens are signed with a publicly known key. Rate limiting is absent on both login and register endpoints.

The frontend and backend disagree on the unit for weight percentages. The AddSubjectModal and AddGradeForm work with integers (60 for 60%), while the Zod schemas enforce `max(1)` (meaning the decimal 0.6). This mismatch makes the create-grade and create-subject flows non-functional unless the user manually types decimals, which the UI doesn't guide them to do.

The Vercel configuration deploys only the frontend static bundle. The `/api` rewrite points at itself (no upstream), so API calls will 404 in production. The backend requires a PostgreSQL connection and a long-running Express process, neither of which Vercel's default serverless model provides out of the box. A split deployment strategy (Vercel for frontend + separate backend host) or Vercel serverless functions wrapping the Express app would be needed.

Internationalization auto-detects the browser locale and supports EN/ES with a manual toggle. The mobile viewport disables user scaling and sets theme-color for a native app feel, with responsive breakpoints throughout — though `user-scalable=no` is an accessibility concern for users who need zoom.

1. **Hardcoded JWT fallback** — `process.env.JWT_SECRET || 'default-secret'` means any deployment without the env var set signs tokens with a known key. Remove the fallback and fail fast at startup if the variable is missing.

5. **No rate limiting on auth endpoints** — Register and login can be brute-forced without any throttling.
6. **Multiple PrismaClient instances** — Each route file instantiates its own `new PrismaClient()`, creating multiple connection pools. Use a shared singleton.

## JWT secret fallback is a fail-open posture

In both `auth.ts` (token generation) and `middleware/auth.ts` (token verification), the code uses:

```ts
const secret = process.env.JWT_SECRET || 'default-secret';
```

If the environment variable is unset — which is the default state for any fresh deployment — all tokens are signed and verified with the string `'default-secret'`. An attacker who reads the source can forge arbitrary tokens. The `.env.example` documents the variable but nothing enforces its presence. The correct pattern is to crash at startup if `JWT_SECRET` is undefined, making misconfiguration impossible to ship silently.

## Frontend-backend weight unit disagreement

The AddSubjectModal manages component weights as integers:

```tsx
const [components, setComponents] = useState([
  { name: 'Catedra', weightPercentage: 60 },
  { name: 'Laboratorio', weightPercentage: 40 },
]);
```

It validates `totalWeight === 100` and sends the payload directly to the backend. The backend's `createSubjectSchema` enforces:

```ts
weightPercentage: z.number().min(0.01).max(1)
```

A value of 60 fails this validation. The identical problem exists in `AddGradeForm`, which sends the integer weight directly while `createGradeSchema` also caps at 1.0.

The fix is either to normalize in the frontend before sending (`weightPercentage / 100`) or to change the backend schemas to accept 0-100 and store accordingly. The current state means no subject with components and no grade can be created through the UI.

## Vercel deployment gap

The `vercel.json` configures:

```json
{
  "rewrites": [
    { "source": "/api/(.*)", "destination": "/api/$1" },
    { "source": "/((?!api/).*)", "destination": "/index.html" }
  ]
}
```

The first rewrite is a self-referential no-op — it rewrites `/api/*` to `/api/*` on the same Vercel deployment, which only serves the frontend static files. There are no Vercel serverless functions (`/api/*.ts` files in the Vercel sense) and no external proxy target. In production, every API call will return 404 or the `index.html` fallback.

The backend is a traditional Express server requiring a persistent PostgreSQL connection. Deploying it to Vercel would require either the `@vercel/node` serverless adapter wrapping the Express app, or pointing the frontend's API calls at a separately-hosted backend (Railway, Fly.io, etc.) and updating `CORS_ORIGIN` accordingly.

## Multiple PrismaClient instantiations

Each route file (`auth.ts`, `periods.ts`, `subjects.ts`, `grades.ts`) creates its own `new PrismaClient()`. In development this leads to connection pool exhaustion during hot-reload; in production it wastes database connections. Prisma's documentation explicitly recommends a singleton pattern. A shared `lib/prisma.ts` exporting a single instance would solve this.

## Period list over-fetches nested data

The `GET /api/periods` endpoint eagerly includes all subjects, components, and grades for every period. For a student with several semesters of data, this query returns the entire grade history on every period-list call. Since the frontend already calls `GET /periods/:id/subjects` separately when a period is selected, the period list could return only period metadata and let the subject fetch happen on demand.

## No rate limiting on authentication

The register and login routes have no throttling mechanism. An attacker can attempt credential stuffing at whatever rate the server can handle. Express middleware like `express-rate-limit` on the `/api/auth` prefix would mitigate this with minimal effort.

## Test coverage shape

The backend has 18 tests, all exercising `gradeCalculator.ts` — a pure function with no I/O. The auth routes, ownership verification logic, Zod validation middleware, and error handler have no test coverage. The frontend has 5 smoke tests confirming the login page renders. No tests exercise the dashboard, grade CRUD flows, or i18n switching.

## SubjectCard duplicates backend calculation logic

`SubjectCard.tsx` re-implements `calculateComponentAverage` and `calculateSubjectAverage` client-side rather than consuming the `calculatedAverage` field the backend already returns in the subjects response. If the averaging formula changes, two implementations must be updated in lockstep. The frontend could trust the backend's computed averages instead.
