# Fix pass for JWT, weight units, Prisma singleton, SubjectCard, and Vercel deployment

The fix commit addresses the five most critical issues from the v1 review: JWT secret now fails fast when unset, weight validation schemas accept integer percentages (1-100) matching the frontend, a Prisma singleton replaces per-route instantiations, SubjectCard consumes backend-computed averages, and a Vercel serverless function wraps the Express app. The fixes are well-targeted — the gradeCalculator tests were updated to use integer weights and all 23 tests pass. Watch for: the serverless function imports the Express app from TypeScript source via a `.js` extension, which won't resolve without a build step that Vercel may not orchestrate correctly for the monorepo layout (likely); JWT secret validation is skipped in the serverless path since `getJwtSecret()` is only called inside the `if (VERCEL !== '1')` startup block (confirmed); no rate limiting on auth endpoints remains unaddressed (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The JWT fix introduces `getJwtSecret()` which throws if the environment variable is missing, but the fail-fast check only executes in the non-Vercel code path (`if (process.env.VERCEL !== '1')`). In the serverless function, the first call to `getJwtSecret()` happens inside route handlers during a request, meaning a misconfigured deployment silently returns 500s on auth attempts rather than failing at deploy time.

The Vercel serverless adapter at `api/index.ts` imports from `../packages/backend/src/index.js` — a path that references compiled output but the `includeFiles` glob only bundles source TypeScript. Vercel's builder would need to either compile the backend first or the import path needs to point at the source `.ts` file with appropriate tsconfig. Given that the backend's `tsconfig.json` uses `"module": "ESNext"` and `"moduleResolution": "bundler"`, the function likely fails at runtime with a module resolution error unless Vercel's `@vercel/node` builder transpiles the entire dependency tree.

Auth rate limiting and API integration tests remain absent, as noted in v1. The period list endpoint still eagerly loads the entire subject/component/grade tree, which will degrade as students accumulate semesters.

## JWT validation gap in serverless mode

The fix correctly introduces `getJwtSecret()` with a throw-on-missing pattern, and it's called at server startup:

```ts
if (process.env.VERCEL !== '1') {
  getJwtSecret(); // validates at startup
  app.listen(PORT, () => { ... });
}
```

But the serverless handler in `api/index.ts` never triggers this block — `VERCEL` is always `'1'` in that environment. The first invocation of `getJwtSecret()` happens inside `generateToken()` or `authenticate()` during an actual request. If `JWT_SECRET` isn't configured in Vercel's environment variables, every auth request silently throws an unhandled error that the global error handler catches and returns as a generic 500. The fail-fast intention is defeated.

A straightforward fix: call `getJwtSecret()` at module scope in `lib/jwt.ts` (outside any function), so the module fails to load if the secret is missing. This crashes the serverless cold start immediately, which Vercel surfaces as a deploy-time error.

## Serverless function import path uncertainty

```ts
// api/index.ts
import app from '../packages/backend/src/index.js';
```

The backend's `tsconfig.json` outputs to `dist/`, and the source files are `.ts`. The `.js` extension in the import relies on TypeScript's ESM convention where `.js` resolves to the corresponding `.ts` file during compilation — but this only works when the importing file and the imported file share a compilation context. The `api/index.ts` file sits at the repo root, outside the backend's `tsconfig.json` scope.

Vercel's `@vercel/node` builder does handle TypeScript transpilation, but it processes `api/index.ts` as a standalone entry point. Whether it follows the `../packages/backend/src/index.js` import and transpiles the entire backend dependency tree (including Prisma client, bcrypt native bindings, and the shared package) depends on Vercel's internal bundling. The `includeFiles: "packages/backend/**"` helps with file availability but doesn't guarantee module resolution.

A more robust approach: have the Vercel build step compile the backend first (`prisma generate && tsc` in the backend package) and import from the compiled output, or use `vercel.json`'s `buildCommand` to ensure the backend is built before the function is bundled.

## Auth rate limiting (unchanged from v1)

The `/api/auth/register` and `/api/auth/login` endpoints have no throttling. Adding `express-rate-limit` scoped to the auth router (e.g., 5 attempts per minute per IP) would mitigate brute-force and credential stuffing attacks with minimal code.

## Period endpoint over-fetching (unchanged from v1)

```ts
const periods = await prisma.period.findMany({
  where: { userId: req.userId },
  orderBy: { createdAt: 'desc' },
  include: {
    subjects: {
      include: { components: { include: { grades: { orderBy: { order: 'asc' } } } } },
    },
  },
});
```

This loads the full grade tree for all periods. Since the frontend already fetches subjects per-period via `GET /periods/:id/subjects`, the period list could return only period metadata (`id`, `name`, `createdAt`).
